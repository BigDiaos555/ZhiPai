# 数据存储与迁移

目标：**数据跟着 `.app` 走**。把整个 App 拷到另一台 Mac，双击就能看到原来那套排课数据，
不需要拷 `~/Library`、不需要账号、不需要任何配置。

## 1. 数据到底放在哪

| 位置 | 角色 |
| --- | --- |
| `<App>.app/Contents/Resources/userdata/store.json` | **唯一权威副本**。App 自己维护，随 App 一起拷贝 |
| `<App>.app/Contents/Resources/userdata/store.json.bak` | 本次会话开始前的快照，主文件读坏时自动回滚 |
| `~/Library/WebKit/<bundle id>/` | 旧版本的数据来源 + 运行期缓存。可以整个删掉，不影响数据 |
| `~/Library/Application Support/<bundle id>/userdata/` | 仅在 App 所在位置不可写时启用的退路（见第 6 节） |

`store.json` 是明文 JSON，`keys` 里就是网页 `localStorage` 的原样字符串：

```json
{
  "format": "zhipai-vault-1",
  "app": "智能教务",
  "bundleId": "com.zhipai.paike",
  "savedAt": "2026-11-10T06:45:02Z",
  "keys": {
    "zhipai.state.v3": "{\"meta\":{...},\"classes\":[...],\"lessons\":[...]}",
    "zhipai.semesters.v1": "{\"activeId\":\"sem_...\",\"list\":[]}",
    "zhipai.zoom": "1",
    "zhipai.mtmode": "week"
  }
}
```

菜单「智能教务 → 在访达中显示数据文件」可以直接定位它。

### 为什么不用 localStorage 本身

`WKWebView` 的 localStorage 物理位置固定在 `~/Library/WebKit/<bundle id>/WebsiteData/Default/<hash>/…`
（两级哈希目录名），**没有公开 API 能改路径**。数据放那儿，拷 App 就是拷一个空壳。
所以改成：**网页照旧用 localStorage，但那是一个垫片**，真正的存储由原生外壳接管。

## 2. 一次读写的完整链路

```
网页  localStorage.setItem(k, v)
  │   ↓ 垫片：先写内存（同步，语义和真 localStorage 一致，含 length / key(i) / clear）
  │   ↓ 250ms 合并一次
  ├─ postMessage({cmd:'vault', keys: 全量键值})
  │
原生  合并 → 0.45s 去抖 → 写 store.tmp → rename() 原子替换 store.json
  │                     ↓
  └─ 标记「封条失效」→ 空闲 20s 后重签名；退出时强制重签名
```

要点：

- **读是同步的**。页面加载时整份快照已经塞进内存（`window.__ZHIPAI_VAULT_SEED__`），
  所以 `DB.load()` 这类同步读取不会有任何等待或闪烁。
- **写是全量覆盖**，不做增删增量。代价是一次多传几百 KB，好处是不会出现「删掉的键又被加回来」
  这类状态不一致，损坏时也只是一份完整的旧数据。
- **`rename()` 原子替换**：任何时刻磁盘上要么是旧的完整文件、要么是新的完整文件，
  拷贝过程中途断电也不会得到半截 JSON。
- 同时仍会往 WebKit 的 localStorage 写一份（纯缓存，为了兼容旧版本回退）。

## 3. 老版本升级：数据自动搬家

新版本第一次启动时 `store.json` 还不存在，垫片会把 WebKit 里现存的 localStorage **整体**搬进来，
并立刻落盘：

- 判断依据是原生传下来的 `firstRun`（= 包内没有 `store.json`）；
- 首次搬迁走的是「立即写」，不等去抖计时器 —— 用户开一下马上退出也不会丢；
- 搬完之后 `firstRun` 变 false，以后不再从 WebKit 读，避免旧缓存把新数据覆盖掉。

升级前后的数据是同一份：实测正式版 `zhipai.state.v3` 从 localStorage 的 207 052 字节（UTF-16LE）
变成 `store.json` 里的 103 526 字符，逐字节对应。

## 4. 拷贝到另一台 Mac

1. **先退出 App**（⌘Q）。退出时会强制重签名，保证包内是一份「封条完好」的 App。
2. 用 Finder 把 `智能教务.app` 拖到 U 盘 / 局域网共享，或者右键「压缩」成 zip 再传。
3. 目标机：拖进「应用程序」文件夹，双击。第一次会被 Gatekeeper 拦一次
   （App 是 ad-hoc 签名、没有公证），到「系统设置 → 隐私与安全性 → 仍要打开」放行一次即可，
   之后正常双击。
4. 打开后看到的就是原来那套数据；菜单「关于」里会显示数据位置。

验证是否真的带过去了（可选）：

```bash
"/Applications/智能教务.app/Contents/MacOS/zhipai" --vaultinfo
# vault=/Applications/智能教务.app/Contents/Resources/userdata/store.json
# portable=yes
# keys=5
```

**不要**在 App 运行时用 `cp -R` / `rsync` 边跑边拷：虽然 `store.json` 是原子替换不会被拷成半截，
但那时封条可能处于失效窗口（刚写完、还没重签名），拷过去会被判「已损坏」。

## 5. 签名与「封条」（这一节最反直觉）

App 的每个资源文件都在代码签名的封条（`Contents/_CodeSignature/CodeResources`）里。
**往 `Contents/Resources` 写数据，必然让签名校验失败**，这是 macOS 的规则，绕不过去：

```
# 干净构建
$ spctl -a -vvv --type execute 智能教务.app
智能教务.app: rejected                    ← 未公证，属于正常状态，可「仍要打开」

# 写了一次数据之后（未重签名）
$ spctl -a -vvv --type execute 智能教务.app
智能教务.app: a sealed resource is missing or invalid   ← 到别的机器上会显示「已损坏」，没有放行按钮
```

所以外壳在三个时机自动重签名（`codesign --force --sign -`，约 20ms，ad-hoc）：

| 时机 | 目的 |
| --- | --- |
| 写盘后空闲 20s | 日常使用中封条基本一直是完好的 |
| 退出 App | 保证「拷走的那一份」永远签名完好 |
| 启动时 `codesign --verify` 不通过 | 崩溃 / 强制退出 / 从别处拷来的旧副本，开机即自愈 |

实测：**运行中对自身重签名是安全的**（`codesign` 只替换签名段，主可执行文件的代码页没有变化，
进程不会被打断）。重签名会顺手跑一遍 `--verify --strict`，失败只写日志、不影响使用。

失败也不会伤数据：数据文件本身是普通 JSON，签名只影响 Gatekeeper 的放行判断。

## 6. 路径、权限、环境差异

### 路径

- 所有路径都从 `Bundle.main.bundleURL` 推导，**不写死任何绝对路径**，App 改名、换目录都不受影响。
- 数据文件名固定为 `userdata/store.json`，与安装位置无关。
- 用户主目录不同（不同账号）也不影响：包内数据优先，找不到才看 `~/Library/Application Support`。

### 只读位置（磁盘映像 / 下载目录）

两种情况会让 App 包不可写：

1. 直接在 `.dmg` 里双击运行；
2. 从浏览器 / 聊天软件下载后直接在「下载」里打开，触发 Gatekeeper 的路径随机化（App Translocation），
   系统会把 App 挂到一个**随机只读路径**上运行。

此时 `Vault` 会真写一个探针文件来确认不可写，然后：

- 数据退到 `~/Library/Application Support/<bundle id>/userdata/store.json`，功能完全正常、不会丢；
- 启动时弹一次提示，说明「拷 App 不会带走数据」以及怎么修；
- 用户把 App 拖到「应用程序」后重新打开，**会自动把退路目录里的数据接回包内**（日志里有
  `已从 Application Support 接回 N 项旧数据`），之后就可以正常携带了。

### 权限

- App **没有**开沙盒、没有 entitlements，只需要对自身 bundle 的普通写权限；
- 放在 `/Applications` 且属于当前用户（正常安装方式）时可直接写；
- 若 App 属于 root 或被系统策略锁定，写入失败 → 自动走退路目录 + 提示，不崩溃。

### 架构与系统版本

- 可执行文件是 **arm64 + x86_64 通用二进制**，Apple 芯片与 Intel Mac 都能直接跑，无需 Rosetta 转译。
- 最低系统 macOS **13.0**（`LSMinimumSystemVersion`）。为什么是 13：Command Line Tools 里的
  `libswiftCompatibility*.a` 只有 arm64 切片，交叉编 x86_64 时低于 13 会链接失败。
- 两个 App（正式版 `com.zhipai.paike` / 演示版 `com.zhipai.paike.demo`）bundle id 不同，
  数据仓库天然隔离，可以同机共存。

### 多份副本

同一个 App 复制成两份分别使用（比如办公室放一份、家里放一份）：**各自写各自的 `store.json`**，
互不干扰，但也互不同步。想让两份一致，用「拷 App」的方式整体替换，而不是让它们同时打开对着改。
注意两份的 bundle id 相同，共享 `~/Library/WebKit/…` 缓存目录——那只是缓存，不影响数据正确性。

### 机房 / 网络盘

把 App 放在 SMB / NAS 上给多台机器共用时，写入取决于共享盘的权限与文件锁支持，
并会出现多人同时写同一份 `store.json` 的情况（最后写的覆盖前面的）。
这种场景建议每台机器拷一份本地副本。

## 7. 备份与恢复

- **备份**：直接拷贝 `Contents/Resources/userdata/store.json`（或者整个 App）。
- **恢复**：把它放回 `Contents/Resources/userdata/`，启动即可（App 会自己重签名）。
- **防损坏**：主文件读不出来时自动回滚 `store.json.bak`（本次会话开始前的快照）。
- **彻底重来**：删掉 `store.json` 再启动，等于回到内置的初始数据；但注意 WebKit 里的旧缓存会在
  这次「首次启动」被重新搬进来，要彻底清空得把 `~/Library/WebKit/<bundle id>` 一起删掉。

## 8. 排查

| 现象 | 原因 / 处理 |
| --- | --- |
| 换了机器数据是空的 | 拷贝时 App 还在运行，或当时 App 位于只读位置（`--vaultinfo` 看 `portable`） |
| 提示「数据暂存在 App 之外」 | App 在磁盘映像 / 下载目录里，拖进「应用程序」重开即自动接回 |
| 另一台机器提示「已损坏」 | 见到的是拷贝时封条失效的中间状态；在本机正常退出一次让 App 重签名，再重新拷 |
| 提示「无法验证开发者」 | 正常的未公证提示，到「隐私与安全性 → 仍要打开」放行一次 |
| 想确认数据在不在包里 | `.../Contents/MacOS/zhipai --vaultinfo`，或菜单「在访达中显示数据文件」 |

自检钩子（改完代码回归用）：

```bash
BIN="dist/智能教务.app/Contents/MacOS/zhipai"
"$BIN" --vaultinfo   # 仓库路径 / 是否便携 / 键数，日志在 /tmp/zhipai-vault.log
"$BIN" --vaulttest   # 走一遍「垫片生效 → 写标记 → 落盘 → 重载页面后仍在」，日志在 /tmp/zhipai-vaulttest-1.log、-2.log
```
